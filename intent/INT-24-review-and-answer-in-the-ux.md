# Intent: Review, approve and answer plans and intents in the UX

## Problem
Intents and plans are reviewed, approved and answered in the GitHub pull-request editor today. It is a bad experience: the text is full of raw markdown codes, so the person reads symbols instead of the document, and answering an open question means editing those codes by hand. The people who must approve (the owner, reviewers) are often not the people who are comfortable in markdown. The approval itself, a name and a date typed into a line, is easy to get wrong or to leave out.

## Proposed outcome
A page in the Manifold UX where a signed-in person opens an intent or a plan and reads it as a formatted document, not as markdown. From that page they can:

1. **Approve or reject it.** Approval fills in the document's own approval line (`accepted_by` for an intent, **Approved by** for a plan) with the person's name and a timestamp the system generates. Rejection requires a reason and records who, when and why.
2. **Answer its open questions.** Each question in the document has an answer field. The answer is saved into the markdown beside the question, in the form the existing intents already use (`Answer: ...`), with who and when.

The markdown file remains the source of truth. Everything the page does is a plain, readable, diffable change to that file.

**How this relates to INT-12 (decision: new intent, no amendment).** INT-12 is a writing tool: a person and a model draft a new intent, with a model side panel. This intent is a reading, deciding and answering tool for finished intents and plans, with no model, and it covers plans, which INT-12 puts out of scope. The overlap is small: both save a markdown document through the server and both change status only by a person. Where the editor component can be shared (the preview, the save path) it is reused, not rebuilt. INT-16 supplies the queue of what waits for review; this intent is the page a reviewer lands on from that queue.

## Affected users and systems
- **The owner and reviewers,** who approve, reject and answer.
- **Analysts and authors,** who see rejections and answers come back.
- **The interface** (INT-9) and its design (INT-8); **the intent editor** (INT-12) for shared components; **the review queue** (INT-16) as the entry point.
- **The server,** which writes the change, and the sign-in and identity it relies on (INT-1, INT-7).
- **The GitHub store and pull-request flow** (INT-14, INT-16), if the change reaches the repository that way.
- **The intent and plan templates** in `docs/templates/`, which define the lines being filled in.

## Constraints
- **The markdown is the source of truth.** The page reads and writes the file; it keeps no second copy of an approval or an answer. The result stays readable as plain markdown and shows as a small, reviewable diff.
- **Rendered, not raw.** The page shows the document as formatted HTML. The rendering is sanitized: no script, no remote images or fonts (INT-8 offline-clean).
- **Identity comes from the sign-in.** The name written on an approval, a rejection or an answer is the signed-in person's identity (INT-7, INT-1), never typed in or claimed by the caller. The timestamp is generated by the server, in a fixed format, and cannot be edited on the page.
- **A person approves; nothing else does.** No agent, script, model or service credential can approve, accept or reject on a person's behalf. Approval requires an interactive signed-in person; the page offers no way to approve through an API key or a bulk action.
- **Roles.** Who may approve an intent or a plan, and who may only answer, follows the roles of INT-1; the page does not widen them. A person without the right sees the document and no approve or reject control.
- **Rejection carries a reason.** A rejection without a written reason is not accepted. The reason is recorded in the document and is visible to the author.
- **An answered question is recorded in place.** The answer sits next to its question, with who and when. The original question is kept. A later change to an answer is a new, dated answer or a visible edit in history, not a silent overwrite.
- **Approval is tied to a version.** An approval applies to the exact text the person saw. If the document changed after it was opened, the approval is refused and the person sees the change first.
- **Concurrent edits are never silently merged.** A save against a stale version is refused as a conflict, and the person sees both versions (the rule of INT-14 and INT-16: no silent overwrite, no silent merge).
- **Status changes only by the form, not by raw editing.** Approving or rejecting changes the approval line and status fields in one step; the page does not let a person set another person's name.
- **Works with local and GitHub stores.** Local-only instances keep working; behavior is the same as seen by the person.
- **Accessible** to the standard set in INT-8: keyboard use, visible focus, readable contrast.
- **What the page must not do.** It must not approve automatically on open or on a timer, pre-tick an approval, write an approval for someone else, hide the rejection reason, edit the document outside the approval, rejection and answer fields, or send the document text to an outside service.

## Scenario seeds

### S1 — Read it as a document
**Who:** A reviewer who does not live in markdown.
**Wants:** To open an intent or plan and read it formatted.
**So that:** They review the content, not the symbols.
**We will know when:** Opening a plan from the queue shows headings, lists, tables and links as formatted text, and no `#`, `**` or pipe characters are visible.
**Must never:** Run script from the document or load anything from outside.

### S2 — Approve with a generated timestamp
**Who:** The owner.
**Wants:** To approve a plan with one action.
**So that:** The approval is correct and cannot be mistyped.
**We will know when:** After they confirm, the plan's **Approved by** line holds their signed-in name and a system-generated timestamp, the change appears in history under their identity, and the page shows it.
**Must never:** Let an agent, a script, a service credential or the page itself approve on someone's behalf, or let the person type or alter the name or the timestamp.

### S3 — Reject with a reason
**Who:** A reviewer who finds the plan unfit.
**Wants:** To reject it and say why.
**So that:** The author knows what to fix.
**We will know when:** The reject control stays disabled until a reason is entered; afterward the document shows the rejection with who, when and the reason, and the status is not approved.
**Must never:** Record a rejection without a reason, or discard the reason.

### S4 — Answer an open question
**Who:** The owner, with a list of open questions in an intent.
**Wants:** To type an answer beside each question.
**So that:** The author or planner can act on it without editing markdown.
**We will know when:** Each open question shows an answer field; after saving, the markdown has the answer under its question in the existing `Answer:` form, with who and when, and the question text is unchanged.
**Must never:** Change, reorder or delete the question, or save an answer under a different question.

### S5 — Someone else changed it first
**Who:** Two reviewers on the same document.
**Wants:** Neither to lose work.
**So that:** The document stays consistent.
**We will know when:** The second save, made against an older version, is refused with a message, and the person sees what changed and can re-apply their answer or approval.
**Must never:** Overwrite the other person's change silently, or approve text the person did not see.

### S6 — Only the right people approve
**Who:** A contributor who can read the intent.
**Wants:** To read it, and perhaps answer questions.
**So that:** Approval stays with those entitled to give it.
**We will know when:** A person without the approval right sees no approve or reject control, and a direct request to approve is refused and logged.
**Must never:** Treat "cannot check the role" as "allowed".

### S7 — The file stays a plain file
**Who:** An author who reads the diff.
**Wants:** The approval and answers to be ordinary lines of markdown.
**So that:** Review in git still works and nothing is hidden in a database.
**We will know when:** The commit or pull request for an approval shows only the approval line, status and timestamp changed, and the file reads correctly in any markdown viewer.
**Must never:** Store the approval anywhere the file does not show.

## Out of scope
- Writing an intent with a model as partner (INT-12) and a general page editor.
- Editing the body of an intent or plan beyond the approval, rejection and answer fields.
- The review queue itself and the pull-request policy (INT-16); the GitHub store (INT-14).
- Reviewing code or pull-request diffs.
- Test plans, review documents (`REVIEW_PLAN_X.md`) and held-out scenarios; extending to them is a later decision.
- Comments or threads on arbitrary passages of text.
- Notifying people by email or chat.

## Open questions
- How does an approval or answer reach the repository: a direct commit through the server, a pull request, or a local file change? INT-14 gives the server a GitHub write path and INT-16 sets the pull-request policy, but neither says which applies to editing an intent or plan. A direct commit is simplest; a pull request fits "a person approves what needs a person" and would let the approval be reviewed too. Tied to INT-12's open question on the same choice. (the product owner)
- Where do intents and plans live for the UX: as wiki pages in the instance (as INT-12 assumes) or as files in the product repository under `intent/` and `docs/plans/`? The page must write the same file the agents read. (the product owner)
- Which roles may approve an intent, and which a plan? Today the rule is "a human"; INT-1 roles do not yet name this, and INT-23 is deciding the review policy. Is the owner the only approver? (the product owner)
- What exactly is written as the approver: the GitHub account name, the display name, or both, in the form `Michael Hay 2026-11-07` already used in `accepted_by`? And in what time zone and format is the timestamp? (the product owner)
- Does approval of a plan or intent also set `status: accepted` in the same change, and what does a rejection set it to (stays `draft`, or a new `rejected` value, which the template does not have)? (the product owner)
- Should approving after any edit require a fresh re-open (version tied), or may a trivial edit keep the approval? (the product owner)
- When a reviewer answers a question, who tells the author or the planner: only the git history, or a marker in the queue? (the product owner)

## Concerns flagged
- **Approval write-back.** The approval line is currently a hand-typed convention; making the UX write it is a new trust path. It depends on INT-7 sign-in being built and on INT-1 deciding who may approve. If INT-9 ships before those, this intent cannot be built safely. The owner decides the order.
- **Rejected status.** The template defines `draft | accepted | closed` only. A rejection recorded without a status value is ambiguous; adding one changes the template and agent rules, which this intent does not do.
- **Shared token risk.** If the UX writes through the server using one service credential, the history would show the service, not the person, which breaks the identity constraint. INT-9 S3 already forbids this; it must hold here.
- **Agent rules.** Current agent rules forbid an agent filling in **Approved by**. That rule stays; the UX is the human path. The agents' definitions may need a line saying where a human now approves.
